# Royalty OS v0.4 Structural Diff

**Subtitle:** From Review-Support Architecture to Dynamic Value Relationship OS
**Version:** v0.4 Draft
**Status:** Structural Diff Draft
**Previous Version:** Royalty OS v0.3
**Recommended File:** `docs/v0.4-structural-diff.md`

---

## 1. Purpose

This document defines the structural difference between **Royalty OS v0.3** and **Royalty OS v0.4**.

Royalty OS v0.3 established a review-support architecture for value relationships.
Royalty OS v0.4 extends that foundation into a dynamic value relationship operating system.

The purpose of this document is to clarify:

* what was established in v0.3,
* what is extended in v0.4,
* what is intentionally not included in v0.4,
* and how future schemas, examples, and validators should be derived.

This document should be created before JSON Schema, examples, validators, or GitHub Actions are added for v0.4.

The main transition is:

```text
v0.3 = make value relationships reviewable
v0.4 = make value relationships governable and evolvable
```

Royalty OS v0.4 does not automatically decide value.
It structures dynamic value relationships so that humans and AI systems can review, govern, and evolve them responsibly.

## 2. v0.3 Baseline

Royalty OS v0.3 established the following baseline architecture:

```text
Royalty OS v0.3
= Policy-Guided Value Graph Architecture
```

The core principle of v0.3 was:

```text
Royalty OS v0.3 does not decide value automatically.
It structures value relationships so that humans and AI can review them responsibly.
```

### 2.1 Core Components in v0.3

v0.3 introduced four major architectural pillars:

```text
1. Value Graph
2. Policy Engine
3. Scoring Boundary
4. Governance Layer
```

### 2.2 v0.3 Role

v0.3 transformed value records and value events into reviewable relationships.

The basic flow was:

```text
v0.1 = record
v0.2 = event
v0.3 = graph + policy
```

v0.3 made it possible to represent relationships among:

* contributors,
* works,
* prompts,
* outputs,
* references,
* derived artifacts,
* value events,
* and review contexts.

### 2.3 v0.3 Limitations

v0.3 did not fully define:

* dynamic relationship updates,
* governance actions as first-class objects,
* multi-layer value graphs,
* policy modules as separable components,
* boundary separation between scoring and execution,
* OS-level event logs,
* migration logic across graph versions.

These limitations become the design targets of v0.4.

---

## 3. v0.4 Design Direction

Royalty OS v0.4 introduces the following design direction:

```text
Royalty OS v0.4
— Dynamic Value Relationship OS
```

The central shift is:

```text
From:
  review-support architecture

To:
  dynamic value relationship OS
```

v0.4 does not merely describe value relationships.
It defines how value relationships can be updated, reviewed, constrained, logged, and governed over time.

### 3.1 Design Principles

Royalty OS v0.4 follows these principles:

1. **Human-Reviewed**
   Final value interpretation and governance decisions remain subject to human review.

2. **AI-Assisted**
   AI systems may assist in structuring, detecting, comparing, and explaining value relationships.

3. **Policy-Guided**
   Policy modules guide interpretation but do not replace governance.

4. **Boundary-Aware**
   Scoring, review, governance, and execution must remain structurally separated.

5. **Event-Logged**
   Important changes to value relationships should be recorded as OS-level events.

6. **Evolvable**
   Value graphs should be able to evolve without losing compatibility with earlier records.

## 5. Governance Action Extensions

v0.4 introduces governance actions as explicit structural units.

In v0.3, governance existed as a layer.
In v0.4, governance actions become identifiable operations that can be reviewed, logged, and traced.

### 5.1 Purpose

Governance actions define how a value relationship may be handled after review.

Examples include:

```text
acknowledge
flag
defer
merge
split
revise
escalate
reject
archive
```

These are not payment decisions.
They are governance-level actions applied to value relationships.

### 5.2 Governance Action Object

A future v0.4 schema may define a governance action object such as:

```text
governance_action:
  action_id
  action_type
  target_relationship_id
  actor
  reason
  policy_reference
  review_status
  timestamp
```

This document does not finalize the schema.
It only defines the structural need for governance actions.

### 5.3 Governance Action Boundary

Governance actions must not automatically execute compensation, legal claims, or final attribution.

They only structure reviewable operations.

```text
Governance action != automatic execution
Governance action = reviewable structural operation
```

## 6. Multi-Layer Value Graph

v0.4 extends the v0.3 Value Graph into a Multi-Layer Value Graph.

The v0.3 Value Graph represented value relationships.
The v0.4 Multi-Layer Value Graph separates different types of relationships into distinct layers.

### 6.1 Purpose

The purpose of the Multi-Layer Value Graph is to prevent different kinds of value relationships from being collapsed into a single flat structure.

A contribution relationship, a reference relationship, a policy relationship, and a governance relationship should not be treated as the same type of edge.

### 6.2 Proposed Layers

v0.4 may include the following graph layers:

```text
1. Contribution Layer
2. Reference Layer
3. Derivation Layer
4. Review Layer
5. Policy Layer
6. Governance Layer
7. Event Layer
```

### 6.3 Layer Descriptions

#### 6.3.1 Contribution Layer

Represents who or what contributed to a value object.

Examples:

```text
author -> work
prompt -> output
dataset -> model behavior
human idea -> generated artifact
```

#### 6.3.2 Reference Layer

Represents references, citations, inspirations, or traceable influence.

Examples:

```text
document -> cited_output
article -> derived_argument
repository -> implementation_note
```

#### 6.3.3 Derivation Layer

Represents transformation or derivation.

Examples:

```text
draft -> edited_document
prompt -> generated_text
specification -> schema
article -> translated_article
```

#### 6.3.4 Review Layer

Represents review state and human or AI-assisted assessment.

Examples:

```text
relationship -> pending_review
relationship -> approved_for_record
relationship -> disputed
```

#### 6.3.5 Policy Layer

Represents which policy modules apply to a relationship.

Examples:

```text
relationship -> attribution_policy
relationship -> redistribution_policy
relationship -> dispute_policy
```

#### 6.3.6 Governance Layer

Represents governance actions taken on value relationships.

Examples:

```text
relationship -> flagged
relationship -> escalated
relationship -> merged
relationship -> archived
```

#### 6.3.7 Event Layer

Represents OS-level events related to value graph evolution.

Examples:

```text
relationship_created
policy_applied
review_completed
governance_action_recorded
graph_migrated
```

### 6.4 Design Requirement

A future v0.4 Value Graph schema should allow graph layers to be represented separately while remaining connected through stable identifiers.

## 7. Policy Module Architecture

v0.4 extends the v0.3 Policy Engine into a modular policy architecture.

In v0.3, the Policy Engine provided guidance for reviewing value relationships.
In v0.4, policies should be modular, separable, and composable.

### 7.1 Purpose

The Policy Module Architecture allows different policies to be applied to different layers or contexts.

Examples:

```text
Attribution Policy
Contribution Policy
Review Policy
Dispute Policy
Redistribution Policy
Archival Policy
Migration Policy
```

### 7.2 Policy Module Object

A future policy module may include:

```text
policy_module:
  policy_id
  policy_name
  policy_version
  scope
  applies_to
  rules
  review_requirements
  boundary_constraints
```

This document does not define the final JSON Schema.

### 7.3 Policy Module Scope

Policy modules may apply to:

```text
node
edge
graph_layer
governance_action
os_event
migration_event
review_state
```

### 7.4 Policy Composition

v0.4 should allow multiple policy modules to apply to the same value relationship.

Example:

```text
relationship:
  applies_policy_modules:
    - attribution_policy
    - review_policy
    - dispute_policy
```

### 7.5 Policy Boundary

A policy module may guide interpretation.
It must not automatically produce final value decisions.

```text
Policy module = guidance structure
Policy module != final judge
```

## 8. Dual Boundary Model

v0.4 introduces the Dual Boundary Model.

v0.3 defined a Scoring Boundary to prevent automatic scoring from becoming automatic value judgment.
v0.4 extends this into two separate boundaries.

```text
1. Scoring Boundary
2. Execution Boundary
```

### 8.1 Scoring Boundary

The Scoring Boundary separates:

```text
signal assessment
from
final value judgment
```

A score may assist review, but it must not replace review.

Examples of score-like signals:

```text
trace strength
contribution confidence
reference density
derivation proximity
review priority
```

### 8.2 Execution Boundary

The Execution Boundary separates:

```text
governance recommendation
from
automatic execution
```

A governance action may be suggested or recorded, but it must not automatically trigger compensation, enforcement, punishment, or legal consequence.

### 8.3 Boundary Summary

```text
Scoring Boundary:
  prevents scores from becoming final value decisions.

Execution Boundary:
  prevents governance actions from becoming automatic enforcement.
```

### 8.4 Design Requirement

Future v0.4 schemas should clearly indicate whether a field belongs to:

```text
signal
review
policy
governance
execution
```

This reduces the risk of collapsing review-support structures into automated judgment systems.

## 9. OS Event Log

v0.4 introduces the OS Event Log as a first-class architectural concept.

In v0.3, value events and graph relationships could be represented.
In v0.4, changes to the operating structure itself should also be logged.

### 9.1 Purpose

The OS Event Log records important system-level changes, including:

```text
value relationship created
value relationship updated
policy module applied
governance action recorded
review state changed
graph layer added
graph migration performed
compatibility mapping created
```

### 9.2 OS Event Object

A future OS event object may include:

```text
os_event:
  event_id
  event_type
  target_id
  actor
  timestamp
  previous_state
  new_state
  policy_context
  governance_context
  notes
```

This document only defines the architectural requirement.

### 9.3 Difference from Value Event

A value event records a value-related occurrence.

An OS event records an operating-system-level structural occurrence.

```text
Value Event:
  Something happened in the value flow.

OS Event:
  Something changed in the structure that manages the value flow.
```

### 9.4 Event Log Boundary

The OS Event Log is not a surveillance mechanism.
It is a structural accountability mechanism.

It should record meaningful system-level changes, not excessive personal behavior.

## 10. Top-Level Change Log

v0.4 introduces the concept of a top-level change log for structural evolution.

This is different from the repository `CHANGELOG.md`.

The top-level change log inside the v0.4 architecture should track changes to the value relationship structure itself.

### 10.1 Purpose

The top-level change log records high-level changes such as:

```text
graph version updated
policy module replaced
governance rule revised
boundary rule changed
migration applied
layer added
layer deprecated
```

### 10.2 Structural Role

The top-level change log helps future reviewers understand how the OS evolved.

It supports:

```text
auditability
version traceability
migration clarity
governance continuity
```

### 10.3 Difference from OS Event Log

```text
OS Event Log:
  records operational events.

Top-Level Change Log:
  records structural changes to the OS architecture.
```

Both are needed in v0.4.

## 11. Compatibility with v0.3

Royalty OS v0.4 should remain compatible with v0.3 concepts.

v0.4 must not invalidate the v0.3 baseline.

Instead, it should extend v0.3 as follows:

| v0.3 Concept     | v0.4 Extension                  |
| ---------------- | ------------------------------- |
| Value Graph      | Multi-Layer Value Graph         |
| Policy Engine    | Policy Module Architecture      |
| Scoring Boundary | Dual Boundary Model             |
| Governance Layer | Governance Action Extensions    |
| Value Events     | OS Event Log                    |
| Review Support   | Dynamic Relationship Governance |

### 11.1 Compatibility Principle

v0.4 should treat v0.3 records as valid baseline records.

A v0.3 Value Graph should be migratable into a v0.4 Multi-Layer Value Graph.

### 11.2 Migration Expectation

A v0.3 graph may be mapped into v0.4 as follows:

```text
v0.3 value_graph.nodes
  -> v0.4 multi_layer_value_graph.nodes

v0.3 value_graph.edges
  -> v0.4 graph layers:
       contribution_layer
       reference_layer
       derivation_layer
       review_layer

v0.3 policy_engine
  -> v0.4 policy_modules

v0.3 scoring_boundary
  -> v0.4 dual_boundary_model.scoring_boundary

v0.3 governance_layer
  -> v0.4 governance_actions
```

### 11.3 Backward Compatibility

v0.4 should support reading v0.3-style structures where possible.

However, v0.4 may require additional metadata when dynamic governance, layered graphs, or OS event logs are used.

## 12. Non-Goals

The following are not goals of v0.4.

### 12.1 No Automatic Compensation

v0.4 does not automatically calculate, enforce, or distribute compensation.

```text
Royalty OS v0.4 may structure value relationships.
It does not automatically pay royalties.
```

### 12.2 No Final Legal Judgment

v0.4 does not determine legal ownership, copyright status, or enforceable claims.

```text
Royalty OS v0.4 is not a legal authority.
```

### 12.3 No Fully Automated Value Decision

v0.4 does not automatically decide the final value of a contribution.

```text
Scores and policies assist review.
They do not replace judgment.
```

### 12.4 No Universal Policy

v0.4 does not impose one universal governance policy for all contexts.

Different communities, organizations, repositories, and jurisdictions may require different policy modules.

### 12.5 No Premature Schema Lock-In

This document does not define final JSON Schemas.

The schemas should be created only after the structural diff is accepted.

### 12.6 No Validator Before Structural Agreement

Validators and GitHub Actions should not be created until the following are stable:

```text
multi-layer graph model
policy module model
governance action model
dual boundary model
OS event model
```
